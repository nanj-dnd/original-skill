I'd frame this around a slightly provocative argument: **Engineers should use AI coding assistants for almost everything, but they shouldn't outsource their engineering judgement to them.**

For a company all-hands, I'd avoid making this a generic speech about how AI is transforming software development. Instead, make it a practical argument about productivity, engineering quality, accountability, and where we draw the line.

# **Talk: Should Engineers Use AI for Everything?**

5 minutes · Company all-hands · Balanced, thought-provoking

## **1. Suggested outline**

1. **Opening: The uncomfortable question**

   0:00–0:45 · 45 seconds
   - If AI can write 80% of our code, why are we still writing it ourselves?
   - Are we becoming more productive engineers, or just better at prompting?
   - Introduce the central debate.
2. **The case for using AI everywhere**

   0:45–1:45 · 60 seconds
   - Faster prototyping and debugging.
   - Less time spent on repetitive boilerplate.
   - Easier exploration of unfamiliar technologies.
   - More time for architecture, product thinking and problem-solving.
   Key argument: Not using AI when it provides a meaningful advantage is increasingly a competitive disadvantage.
3. **The problem with blind adoption**

   1:45–3:00 · 75 seconds
   - AI can produce code that looks correct but contains subtle bugs.
   - Developers can lose their understanding of the systems they maintain.
   - Security vulnerabilities and technical debt can accumulate.
   - Faster code generation doesn't necessarily mean faster delivery.
   Key argument: Generating code and engineering software are two very different things.
4. **Where should we draw the line?**

   3:00–4:15 · 75 seconds

   Introduce three principles:
   1. **Delegate execution, not responsibility.** AI can write the code, but engineers own the outcome.
   2. **Trust, but verify.** Review, test and understand AI-generated code.
   3. **Use judgement.** The higher the stakes, the more scrutiny the output deserves.
5. **Closing: The engineer of the future**

   4:15–5:00 · 45 seconds
   - The competitive advantage isn't simply knowing how to code.
   - It's knowing what to build, how to evaluate it, and how to use AI effectively.
   - End with the idea that AI shouldn't replace engineering thinking; it should amplify it.

## **2. Opening paragraph**

Recommended opening

Let me start with a question: If an AI assistant can write code faster than most of us, debug problems, generate tests, and even help design entire systems, what exactly should engineers still be doing themselves? And perhaps more importantly, should we be using AI for absolutely everything? I think the answer is almost yes. But there's an important distinction between using AI to become a better engineer and using AI as a substitute for being one. Because while AI is getting remarkably good at writing code, understanding what should be built, knowing whether it's correct, and taking responsibility when something breaks are still fundamentally engineering problems.

## **3. Three memorable lines to work into the talk**

These can give the presentation a stronger identity:

- **"AI makes writing code cheaper. It doesn't make bad engineering cheaper."**
- **"The goal isn't to write less code. It's to solve more problems."**
- **"Don't compete with AI at writing code. Compete at knowing what code needs to be written."**

## **4. My recommendation**

I'd make the entire talk revolve around one distinction:

**What AI should do**

- Generate
- Debug
- Explain
- Prototype
- Automate
- Accelerate

**What engineers must own**

- Architecture
- Judgement
- Verification
- Security
- Trade-offs
- Accountability

**One final thought:** Don't make the conclusion "AI is a tool, not a replacement." That's been said thousands of times. Make it more ambitious:

*The best engineers in the next decade won't necessarily be the ones who can write the most code. They'll be the ones who can turn an idea into a reliable product by orchestrating people, systems and AI better than anyone else.*

That is a much stronger message to leave an engineering team with.
