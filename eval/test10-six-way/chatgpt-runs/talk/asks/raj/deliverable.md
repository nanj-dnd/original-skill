## **2. Opening paragraph**

I want to start with a situation I think most of us have experienced by now. You open Cursor, Claude, or whichever AI coding assistant you prefer, describe what you want to build, and within a few seconds, you have 100 lines of code sitting in front of you. It looks clean, it looks convincing, and for a moment, you feel incredibly productive. And honestly, you probably are. But here's something I've been thinking about: **just because AI can write code faster than we can, does that necessarily mean we're building better software?** I don't think the answer is always yes, and I think that's a conversation worth having.

## **3. Three key arguments to develop**

I'd keep coming back to these throughout the speech.

**Argument 1: AI is an accelerator, not a replacement for judgement.**

- Use it for boilerplate, repetitive tasks, debugging, documentation and exploring unfamiliar code.
- Let it save time on things that don't require your deepest thinking.
- But don't let it make decisions you don't understand.

**Argument 2: The speed-quality trade-off is real.**

- Code that compiles isn't necessarily good code.
- Code that passes a test isn't necessarily robust code.
- AI can introduce unnecessary abstractions, overlooked edge cases and subtle bugs.
- The faster we generate code, the more important thoughtful reviews become.

**Argument 3: Ownership doesn't transfer to AI.**

- If AI writes the code, the engineer still owns the outcome.
- You should be able to explain what the code does and why it works.
- You should be comfortable questioning or rejecting its suggestions.
- Particularly in insurance software, a small defect can have consequences beyond a failed feature.

## **4. The closing thought**

I'd finish with something conversational rather than overly motivational:

I don't think the solution is to use AI less. If anything, I think we should be experimenting with it more. The opportunity is enormous, and I don't think we should ignore it. But I do think we need to change how we measure productivity. It's not about how many lines of code we can generate, how quickly we can close a ticket, or how much work we can delegate to an AI assistant. It's about whether we're actually building better, more reliable software. So my take is simple: use AI, challenge it, learn from it, and let it make you faster. But never switch off your engineering judgement. Because at the end of the day, AI might write the code, but we're still responsible for what we ship.

## **One suggestion from me**

As QA lead, you have an opportunity to make this more interesting than a generic talk about AI productivity.

I'd introduce this distinction:

**AI can help us increase the speed of development. It cannot independently guarantee the quality of the outcome.**

That gives you a natural connection between engineering and QA without making the speech sound like QA is policing developers.

I'd also avoid making this an anti-AI warning. Your position is much more compelling if people leave thinking, "I should use AI more, but I should also be more thoughtful about how I use it."

That's a good message for a 150-person engineering-led company.
