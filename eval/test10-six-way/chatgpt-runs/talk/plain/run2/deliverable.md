I'd recommend taking a nuanced position rather than arguing that engineers should either embrace AI completely or avoid it. The strongest argument is:

**Engineers should use AI coding assistants extensively, but they shouldn't outsource their engineering judgement to them.**

For a company all-hands, I'd make this provocative, practical, and slightly challenging. You want engineers to leave questioning their current workflows.

# **Talk: Should Engineers Use AI for Everything?**

5 minutes

Technology & Engineering

Balanced argument

## **1. Suggested structure**

| Time      | Section         | Key argument                                                            |
| --------- | --------------- | ----------------------------------------------------------------------- |
| 0:00–0:45 | The hook        | AI has fundamentally changed how we write code.                         |
| 0:45–1:30 | The case for AI | Speed, productivity, prototyping and accessibility.                     |
| 1:30–2:30 | The problem     | Overreliance, hallucinations, technical debt and loss of understanding. |
| 2:30–3:30 | The distinction | Using AI to accelerate engineering vs. using AI instead of engineering. |
| 3:30–4:30 | The framework   | What engineers should delegate to AI and what they should own.          |
| 4:30–5:00 | The conclusion  | AI should make us better engineers, not replace our ability to think.   |

## **2. Opening paragraph**

Let's start with a slightly uncomfortable question: **If AI can write 80% of the code we write today, what exactly makes us engineers?**

Over the past couple of years, AI coding assistants have gone from being an interesting experiment to becoming an integral part of software development. We can generate entire functions, debug complicated errors, build prototypes in minutes and even architect applications with a few prompts. And honestly, that's incredible. But I think we're approaching a point where we need to ask ourselves a more important question: just because AI *can* do something for us, does that mean we should let it? Today, I want to explore whether engineers should be using AI for everything, or whether there's still something fundamentally important about the human thinking behind the code.

## **3. Talking points for the main body**

**A. Why we should be using AI more**

- Eliminates repetitive, low-value coding tasks.
- Dramatically reduces the time between an idea and a working prototype.
- Helps engineers explore unfamiliar technologies and codebases.
- Allows smaller engineering teams to achieve more.
- Frees up time for architecture, product thinking and problem-solving.

**B. Where overreliance becomes dangerous**

This is where I'd spend meaningful time because it's the most interesting part of the discussion.

- **Understanding:** Are we actually understanding the code we're shipping?
- **Debugging:** Can we fix something when the AI-generated solution breaks?
- **Security:** AI-generated code can introduce vulnerabilities that aren't immediately obvious.
- **Technical debt:** Generating code is easy; maintaining it for three years is considerably harder.
- **Skill degradation:** If we stop practising fundamental engineering skills, what happens when the tools fail?

**C. The distinction: AI-assisted vs. AI-dependent engineering**

I'd introduce this as the central idea of the talk.

| AI-assisted engineer           | AI-dependent engineer                    |
| ------------------------------ | ---------------------------------------- |
| Uses AI to accelerate thinking | Uses AI to avoid thinking                |
| Reviews generated code         | Blindly accepts generated code           |
| Understands the architecture   | Relies on AI to explain the architecture |
| Uses AI to solve problems      | Cannot solve problems without AI         |
| Owns the final output          | Outsources accountability                |

**D. A practical framework**

Suggest three categories:

- **Delegate to AI:** Boilerplate, documentation, test generation, repetitive refactoring and initial research.
- **Collaborate with AI:** Debugging, code reviews, architecture exploration and implementation.
- **Own yourself:** Engineering decisions, security-critical decisions, system design, validation and accountability.

## **4. Closing statement**

I'd end with something memorable rather than another list of AI benefits.

I don't think the future belongs to engineers who write the most code. Nor does it necessarily belong to engineers who generate the most code using AI.

I think it belongs to engineers who know what to build, understand why they're building it, and know how to use every available tool to build it better.

AI should raise the ceiling of what an engineer can accomplish, not lower the bar for what an engineer needs to understand.

**The goal isn't to become better at prompting AI to write code. It's to become better engineers because AI exists.**

## **One recommendation to make this talk stronger**

Don't make it sound like an anti-AI warning. Engineers have heard enough of those.

Make the central tension about **productivity versus engineering competence**.

A particularly powerful question to introduce during the talk is:

> If tomorrow we took away every AI coding assistant, would our engineering team still be able to build, debug and maintain the systems we've created?

That question could become the centrepiece of the entire five minutes.
