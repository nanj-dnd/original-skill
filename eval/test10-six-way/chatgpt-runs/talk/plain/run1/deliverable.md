I'd recommend taking a **nuanced but slightly provocative position: Engineers should use AI coding assistants extensively, but they shouldn't use them blindly or for everything.**

The strongest argument isn't that AI will replace engineers. It's that engineering is changing from writing code to making good technical decisions, and AI is shifting where human expertise matters most.

Here's how I'd structure your five minutes.

# **All-hands talk: Should engineers use AI for everything?**

**Central thesis:** AI should become an engineer's default collaborator, not their default decision-maker.

## **1. Five-minute speaking outline**

| Time      | Section                     | Key argument                                                                                             |
| --------- | --------------------------- | -------------------------------------------------------------------------------------------------------- |
| 0:00–0:45 | The provocation             | If AI can write code faster, why are we still writing everything ourselves?                              |
| 0:45–1:30 | The case for AI             | Faster development, less boilerplate, debugging assistance, rapid prototyping.                           |
| 1:30–2:30 | The danger of over-reliance | Hallucinated solutions, security vulnerabilities, technical debt, and code nobody understands.           |
| 2:30–3:45 | Where humans matter         | Architecture, judgement, context, product thinking, accountability and reviewing AI-generated code.      |
| 3:45–4:30 | A practical framework       | Use AI for execution, but retain human ownership of decisions and outcomes.                              |
| 4:30–5:00 | The conclusion              | The best engineers won't necessarily write the most code. They'll know what to delegate and what not to. |

## **2. Opening paragraph**

Let me start with a question: if an AI coding assistant can write a function in ten seconds that would take an engineer twenty minutes, why should that engineer spend twenty minutes writing it? It seems like an obvious answer — they shouldn't. But I think this question opens up a much bigger conversation about how we're approaching software engineering today. We're entering a world where writing code is becoming increasingly cheap, but understanding what code should be written, why it should be written, and whether it's actually correct is becoming even more valuable. So, should engineers be using AI for everything? My answer is yes to using it extensively, but absolutely not to trusting it blindly.

## **3. Key talking points**

**Point 1: The productivity argument**

AI coding assistants can:

- Generate boilerplate and repetitive code.
- Accelerate debugging and testing.
- Help engineers explore unfamiliar frameworks.
- Turn prototypes into working implementations faster.

Your argument: Refusing to use these tools is increasingly like refusing to use an IDE because you prefer writing code in a basic text editor.

**Point 2: The hidden cost of over-reliance**

AI-generated code isn't automatically good code.

Three major risks:

- **Understanding debt:** Engineers approve code they cannot explain.
- **Technical debt:** AI optimises for producing an answer, not necessarily maintaining a system.
- **Security and reliability:** Generated code can introduce vulnerabilities, edge cases and subtle bugs.

Your argument: Faster code generation doesn't automatically translate into faster or better software development.

**Point 3: What actually makes a good engineer now?**

The value proposition of an engineer is shifting.

| Traditional emphasis      | Increasingly important         |
| ------------------------- | ------------------------------ |
| Writing code              | Designing systems              |
| Memorising syntax         | Understanding concepts         |
| Manual debugging          | Evaluating AI suggestions      |
| Implementing instructions | Defining the right problem     |
| Individual output         | Orchestrating tools and people |

**Point 4: The framework — delegate, don't abdicate**

I'd leave the audience with three principles:

1. **Delegate execution:** Let AI handle repetitive implementation and accelerate exploration.
2. **Own the decisions:** Engineers must understand architecture, trade-offs and business requirements.
3. **Verify the output:** Review, test, secure and take responsibility for everything that ships.

## **4. Closing statement**

I'd end with something memorable:

> "I don't think the future belongs to engineers who can write the most code, or even engineers who use the most AI. I think it belongs to engineers who know when to use AI, when to challenge it, and when to trust their own judgement. Because ultimately, AI can generate code, but we're still responsible for what we build."

## **One suggestion to make this talk stand out**

Rather than making this a generic presentation about AI, make it a challenge to the engineering team.

Ask them:

**"If you removed AI coding assistants from your workflow tomorrow, how much of your current engineering capability would remain?"**

It's a slightly uncomfortable question, but that's what makes it effective at an all-hands.

The underlying message should be that AI should make engineers more capable, not make their expertise redundant.
