**What everyone gets**
Main claim: "AI coding assistants are a powerful tool, not a replacement — use them for the right things and keep engineers in the loop."
- Angle: balanced "it depends," augment-not-replace
- Examples: good for boilerplate, tests, docs; risky for security, architecture, anything you don't understand

- Reader: the whole company, so engineering specifics are flattened out
- Tone: upbeat, hedged, ends on a safe call for "thoughtful adoption"

**Four questions — reply like `1b 2a 3c 4a`, adding detail where you have it:**

**1. Stance.** The default says "use it for some things, not everything." What do you actually think?
- a) That — judicious use, with limits
- b) Go further in: the cost of *not* using it is now bigger than the cost of using it badly
- c) Pull back: we're shipping code nobody understands, and it's showing
- d) The question is wrong — "for everything" isn't the issue; who reviews and owns the code is

**2. Your real material.** The default uses generic examples. What's one thing that actually happened on your team?
- a) An incident where AI-written code caused a problem (tell me what, briefly)
- b) A time it clearly saved real time or unblocked something (what and roughly how much)
- c) A number — share of PRs with AI-assisted code, review time, bug rate, anything measured
- d) Nothing specific; keep it general

**3. Room and tone.** All-hands means non-engineers are listening. The default is upbeat and simplified for everyone.
- a) Plain and direct, pitched so the whole company follows
- b) Mostly for the engineers; others can follow the gist
- c) More formal — leadership is the real audience
- d) Deliberately blunt, meant to start an argument afterward

**4. The ending.** The default closes with three soft guidelines.
- a) A concrete ask — one rule or change you want adopted
- b) An open question you want the company debating
- c) A short story that makes the point without a rule
