# The Hard Part Moved (5 minutes, company all-hands)

## Opening paragraph (about 45 seconds)

I was asked to talk about whether engineers should use AI coding assistants for everything. My short answer is: for most of the typing, yes. But that's the least interesting part of the question. When writing code gets cheap, building the right thing doesn't get easier. The hard part just moves. It moves out of the editor and into the conversations before anyone opens one: what we're building, for whom, and how we'll know it worked. Almost everyone in this room is part of those conversations. So for the next five minutes I'm not only talking to the engineers. I'm talking to all of you.

## Outline

**0:00-0:45 Opening** (above). Claim: mostly yes for the code; the real question is what changes for everyone else.

**0:45-1:45 What changes when code is cheap**
- One real before-and-after from your team: a piece of work that used to take about a week to build and now takes a day or two. (Pick one you can name; don't use an industry stat.)
- Where the saved time went: the building step shrank. Deciding, clarifying, reviewing and fixing the wrong thing didn't.
- Line to land: "We didn't get faster at knowing what to build. We got faster at building it."

**1:45-2:45 Where "for everything" breaks: vague asks**
- An assistant does exactly what an unclear request says, fast.
- It used to be that an engineer halfway through a build would come back with "wait, what did you mean by...?" Now the build is often done before anyone asks.
- So an unclear ask costs more than it used to: you get a finished wrong thing instead of a question.

**2:45-3:30 What engineers do**
- Yes, use it for the bulk of the code.
- One rule: you merge only what you can explain, because you or a teammate gets paged when it breaks.
- Ask your clarifying questions earlier, before generating, not after.

**3:30-4:30 What everyone else does (the main ask)**
- Write down what "done" looks like before the work starts: who it's for, and how we'll know it worked.
- Expect questions earlier and treat them as the job, not as pushback.
- Judge by outcomes, not volume: more pull requests or features shipped isn't the same as progress.

**4:30-5:00 Close**
- Back to the question: "Should engineers use AI for everything? Mostly, yes. The question that decides whether it works is whether the rest of us keep handing them vague asks."
- End on the single ask: next time you request something, write one sentence about what "done" means.

*Timing: about 700 words spoken in total; the opening is about 120.*
