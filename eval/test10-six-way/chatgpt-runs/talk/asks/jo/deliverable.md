I think the strongest angle here is: **AI should be a default tool in an engineer's toolkit, not a substitute for engineering judgment.**

Given that this is a 60-person e-commerce company and the audience includes everyone, I'd avoid making this a debate about whether AI is good or bad. Instead, make it a practical discussion about how we use it responsibly, where it adds value, and where we need to be careful.

Here's the proposed direction.

## **Talk title**

**"AI Should Write More Code. Engineers Should Think More."**

## **5-minute talk outline**

APPROXIMATELY 5 MINUTES · 600–650 WORDS

0:00–0:45

**1. The reality: AI is changing how we build**

Open with a relatable observation: coding assistants can now write functions, debug errors, generate tests and explain unfamiliar code in seconds.

Pose the question: If AI can do all this, should we let it do everything?

0:45–1:45

**2. Where AI genuinely makes us better**

Practical examples:

- Boilerplate code and repetitive tasks.
- Writing unit tests and documentation.
- Understanding unfamiliar codebases.
- Debugging and exploring alternative solutions.

The point: Spend less time on repetitive work and more time solving meaningful problems.

1:45–3:00

**3. The danger of blindly trusting AI**

AI can produce code that looks correct but isn't.

- It can introduce security vulnerabilities.
- It can misunderstand business logic.
- It can create unnecessary complexity.
- It can make developers dependent on suggestions they don't understand.

A particularly relevant example for e-commerce: a seemingly small change to checkout, pricing or inventory logic can have real business consequences.

3:00–4:15

**4. A practical philosophy for using AI**

Establish three principles:

1. **Delegate, don't abdicate:** Let AI do the work, but retain responsibility for the outcome.
2. **Understand before shipping:** Never merge code you cannot explain.
3. **Use judgment:** The higher the business or technical risk, the more carefully AI-generated work should be reviewed and tested.

4:15–5:00

**5. The takeaway**

AI shouldn't make us less capable engineers. It should make us more capable ones.

Close by encouraging experimentation, sharing effective workflows and maintaining accountability.

## **Opening paragraph**

Here's how I'd open it. Conversational, slightly provocative, but not overly dramatic.

I want to start with a question: how many of us have asked an AI tool to write something for us recently? Maybe it was a piece of code, an email, a spreadsheet formula, or even an idea we weren't quite sure how to approach. The reality is that AI has become incredibly good at taking things that used to require hours of work and getting us 80–90% of the way there in seconds. And that's exciting. But I think there's a question we don't ask ourselves often enough: just because AI *can* do something for us, does that mean we should let it? Today, I want to talk about where AI makes us better at what we do, where it can actually make us worse, and how we can find the balance.

## **One recommendation**

I'd make this talk less about AI coding assistants specifically and more about **the relationship between AI, productivity and accountability**.

That way:

- Engineers get practical advice.
- Non-technical employees can relate to the message.
- Leadership gets a sensible framework for AI adoption.
- You're not advocating for either unrestricted AI usage or unnecessary resistance.

And I'd leave the room with one memorable sentence:

**"AI can generate the output. But we are still responsible for the outcome."**

That's the central message I'd build the entire talk around.
