# AI Coding Assistants: More Isn't the Same as Better

**5-minute all-hands talk, outline and opening**

## Opening paragraph (read word for word, about 45 seconds)

I'm the QA lead, so I want to start with a number from my corner of the building. A year ago our automated test suite had about 2,000 tests, and the nightly run finished in about 20 minutes. Today we have about 9,000 tests, most of them written with AI help, and the nightly run takes three hours. On paper that's a win: four and a half times as many tests. But I'm not sure we're four and a half times safer. My suspicion is that a lot of those new tests check the same things over and over. So when people ask whether we should use AI coding assistants for everything, here's where I land: these tools are very good at making more of something. The question we don't ask enough is whether more is what we needed.

## Outline (talking points)

### 1. Opening: the test suite number (0:00 to 0:45)
- Use the paragraph above.
- Let the "20 minutes to 3 hours" figure land before you move on.

### 2. Where I stand (0:45 to 1:30)
- I'm not against these tools. They save time, and I'm not here to ask anyone to stop using them.
- Where they clearly help: boilerplate, first drafts, repetitive changes, getting unstuck.
- But "for everything" goes too far. Writing code was never the whole job.

### 3. What the test suite shows (1:30 to 3:00)
- AI made *writing* tests nearly free. It didn't make running, reviewing or maintaining them any cheaper.
- A test count is not coverage. 9,000 tests that check the same paths tell us less than they seem to.
- The real costs:
  - **Slower feedback.** A problem that used to show up in 20 minutes now shows up the next morning.
  - **More to maintain.** Every redundant test is one more thing that can break, go flaky, or need updating when behavior changes.
  - **False confidence.** A big, green suite *feels* safe, whether or not it is.
- Bring it back to the room: the tests are just where I can see it. The same thing probably happens with application code. More code goes out faster, and the cost lands on whoever reviews it, tests it or maintains it later.

### 4. A rough line, not a rule (3:00 to 4:00)
- The useful question isn't "AI or no AI." It's "who checks this, and how?"
- Use it freely where you can easily tell whether the output is right.
- Slow down where output can pass for progress just by volume: tests, generated docs, large diffs.
- One habit worth trying: before you keep AI-generated work, ask "what does this give us that we didn't already have?"

### 5. Close: start the discussion (4:00 to 5:00)
- I don't have the answer, and I'd rather we work it out together than have someone hand down a policy.
- Three questions for every team, PMs included:
  1. Where has an AI assistant saved you real time, not just made more output?
  2. Where has it created work for someone downstream: a reviewer, QA, on-call?
  3. Besides volume, what should we measure to know it's helping?
- End with a concrete next step, for example: "Bring your answers to [channel / thread / meeting], and I'll share what we find in the test suite." *(Fill in the right place.)*
